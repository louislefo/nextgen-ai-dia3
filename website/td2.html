1. Step 1: Quorum Voting Engine Architecture (vote_k_sur_n)

When a database query carries financial or operational consequences, relying on a single probabilistic model draw is unacceptable. Pair A (Louis Le Forestier & Maxime Laurent) implemented the production quorum voting engine in td2/skeleton-multi-llm-en.py adhering to five mathematical contract requirements:

Contract Rule 1

Strict Majority Requirement

The threshold k must be strictly greater than half the panel size: len(traces_question) // 2 < k ≤ len(traces_question). Any invalid k raises an immediate ValueError, mathematically preventing conflicting consensuses.

Contract Rule 2

Provider Unicity (Anti-Collusion)

Duplicate proposals from identical (provider, model_requested) pairs raise a ValueError. Quorum diversity requires truly independent architectural paths.

Contract Rule 3

Error Retention in Denominator n

Proposals failing execution (HTTP 429, timeouts, SQL syntax errors) remain counted in the total panel size n but cast zero votes. Infrastructure outages raise the barrier to consensus rather than lowering it.

Contract Rule 4

Deterministic Abstention

If no candidate integer value reaches at least k votes, the engine returns consensus: False and value: None. Under no circumstances does the engine fabricate an answer or take an average.

Engine Interface & Return Payload

Synthetic Test Suite Validation (atelier-vote.py)

The consensus engine was certified against four synthetic edge-case scenarios:

  • Agreement (3-of-3): Inputs [100, 100, 120] with k=2 → consensus: True, value: 100, votes: 2 (Consensus reached).
  • Disagreement (1-1-1 Dispersion): Inputs [100, 110, 120] with k=2 → consensus: False, value: None, votes: 1 (Safe abstention).
  • Unavailable / Timeout: Inputs [100, None, None] with k=2 → consensus: False, value: None, votes: 1 (Denominator n=3 preserved, abstention).
  • Correlated Error: Inputs [0, 0, 100] with reference 100 → consensus: True, value: 0, votes: 2 (Demonstrates that a quorum filters independent noise, but cannot fix correlated failure modes without external checks).

Key Finding 1

C09 False Consensus Elimination

In 2-of-3, two different models (Cohere & Qwen) both returned 0 due to independent date syntax bugs, triggering a False Consensus on 0 (ground truth: 487,980). Key Finding 2

C19 Ground Truth Recovery

On question C19, the 2-of-3 panel abstained due to total dispersion (1 vote for 1,990, 1 for 13,930, 1 for 83,580). The 3-of-5 quorum recovered the true ground truth (1,990 cents) with 3/5 votes (GPT-120B, GPT-20B, Dots-Studio), converting an abstention into an automated success.

Key Finding 3

Resilience to Rate Limits (HTTP 429)

On C16 and C20, Qwen exhausted Groq's 1,000 OTPM quota. Under the quorum contract, Qwen remained counted in n=3 and n=5, but healthy models formed clear majorities (2/3 and 4/5), demonstrating operational resilience without lowering the consensus threshold.

3. Step 2: Shared False Consensus Investigation (Group B)

Group B (Baptiste Noailhac, Jean Jaunet, Romain Thepaut) audited the 100 TD 1 cells for shared incorrect values, identifying question C09 as the sole false consensus that wins the 2-of-3 vote.

Why Independent Models Converged on Zero: The “Attractor State”

Question C09 asks for revenue from customers aged exactly 25 on 2026-09-26 (birth date window: 2000-09-27 to 2001-09-26 inclusive). Both failing models missed this window entirely through two completely unrelated errors:

  • Cohere (north-mini-code): Attempted to compute age as CAST(SUBSTR(birth_date,1,4) AS INT) - CASE ..., which evaluated to the birth year minus a correction (~2000), never subtracting from 2026. The condition ... = 25 matched 0 rows.
  • Qwen (qwen3.8-27b): Subtracted the order date o.date instead of the reference date, and forced contradictory conditions: birth_date >= '2001-09-26' AND birth_date <= '2001-09-25', which is logically impossible and matched 0 rows.

The Zero Attractor State in SQL

In SQL aggregations, any query whose WHERE filter selects zero rows returns NULL, which COALESCE(SUM(...), 0) converts to 0. Distinct, uncorrelated semantic errors naturally collapse into 0. Agreement on zero is therefore weak evidence and requires an explicit verification guardrail.

Queue Priority Analysis: Allocation vs. Free Deferral

In atelier-routage.py, the choose scheduler examines resources in a strict order:

  1. Available routes with zero cash cost (including subscription allocations where capital expenditure is already sunk).
  2. Free refill routes that reset within the request deadline (action: defer).
  3. Paid on-demand routes within budget (action: run with cash spend).
  4. Safe abstention when no route meets the quality, deadline, or budget constraints.

Why an available allocation beats waiting for a free refill: Consuming pre-purchased allocation delivers immediate responses with zero latency penalties and avoids queuing overhead. This priority reverses only when allocation is scarce/metered and the request is latency-tolerant (e.g. nightly batch).

Limitations we state rather than hide

Twenty questions across five models support a batch-specific hypothesis, not a general error rate. F2b rests on a single cell, so “100%” there means 1/1. The 3-of-5 quorum reached 100% precision on this batch because one extra model happened to be correct on C09 and another happened to be rejected; the measured claim is that widening the panel suppressed this error, not that a quorum cannot produce a wrong consensus.
